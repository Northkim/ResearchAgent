# 0042: Reviewed prepared Experiment default path

- Status: Accepted
- Date: 2026-08-17

## Context

The default ReAgent Owner is a methodology-capable researcher who must not need
Python, Git, manifests, dependency files, entrypoints, checksums, or
ResourceReference concepts. EP-A established provider-neutral preparation and
approval contracts, while historical Experiment 0.4 remains the advanced exact
owner-staged package path.

## Decision

Publish additive Experiment 0.5.0 / Capsule 0.8.0 producing
`experiment-record/v3` for `PREPARE_WITH_REAGENT`. It remains the existing
Reproduction & Experiment Workflow, consumes one exact selected Idea, requires
no ResourceReference, and prepares bytes only inside its authorized local
Capsule.

Codex performs methodology-aware reasoning and produces a typed implementation
specification only after material scientific questions are resolved. Executable
bytes are rendered by the reviewed deterministic
`SKLEARN_TABULAR_CLASSIFICATION_V1` Builder, not arbitrary Codex code generation.
Both design and exact execution require separate checksum-bound Owner approvals.
The prepared package is content-addressed and provider-neutral. The historical
Experiment 0.4 bounded no-egress process engine remains the sole runner.

## Consequences

Automatic preparation is initially limited to the reviewed KNN/Wine family and
fails `AUTOMATIC_PREPARATION_UNSUPPORTED` outside it. Dependencies must already
exist locally; no preparation or execution stage may install them. Exact
execution/evaluation evidence is durable, and interruption after a consumed run
resumes at Owner review rather than rerunning. Git is neither initialized nor
required. EP-B2 presentation persistence, EP-C local-project adaptation, and
EP-D downstream consumers remain separate work.

The publication is implemented but EP-B1 qualification remains blocked until
the supported runtime has the approved dependencies and the Owner completes the
real methodology checkpoint. Auxiliary-environment execution is evidence of
Builder behavior, not supported-runtime qualification.

## Alternatives considered

Arbitrary Codex-generated executable code was rejected because the current
runner is not a hostile-code sandbox. Requiring Git/GitHub was rejected because
programming expertise is not a default prerequisite. A second execution engine
and a sixth Workflow were rejected because preparation converges on the existing
validated-package and bounded-runner seams. Installing dependencies during a run
was rejected because it violates the no-network, exact-runtime boundary.

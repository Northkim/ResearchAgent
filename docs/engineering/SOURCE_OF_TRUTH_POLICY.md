# ReAgent source-of-truth policy

Status: Owner-ratified engineering policy; implementation not authorized

This policy governs future engineering change packets. It does not change any
product, runtime, schema, version, or accepted architecture decision.

## Authority precedence

Use the first applicable, sufficiently specific source in this order:

1. explicit owner-approved current decisions and accepted ADRs;
2. immutable machine schemas, migrations, Registry publication facts, released
   identities, and checksums;
3. current Capsule compiler, renderers, validators, and Workspace root client;
4. backend domain services, API contracts, repositories, and ORM mappings;
5. frontend consumers and manually maintained types;
6. executable tests and independently maintained golden fixtures;
7. current user-facing documentation;
8. historical `.agent_read` handoffs and progress notes;
9. generated runtime files and caches.

The product plan remains the governing statement of product intent. This
precedence resolves implementation evidence; it does not allow a migration or
test to silently replace owner intent.

## Specificity and time

- A newer, more specific accepted ADR may supersede an older decision within
  its declared scope.
- Accepted ADRs are append-only. Reversal requires a superseding ADR.
- A newer generic note does not override an older specific immutable release
  contract.
- A deployed or published historical version remains authoritative for its own
  bytes even when a newer version changes behavior.
- `review_status=REVIEWED` and `core_capability_maturity` are separate facts.

## Evidence rules

- Tests do not outrank an immutable contract merely because they pass.
- A test whose expected value is generated by the implementation under test is
  implementation-coupled evidence, not an independent golden.
- Synthetic fixtures must be labelled synthetic.
- A lower evidence-level PASS cannot overwrite a higher evidence-level FAIL.
- Owner-observed product evidence must not be normalized or reinterpreted to
  make a fixture pass.
- Generated runtime state proves that an occurrence was observed. It is not by
  itself product-design authority.
- User documentation can reveal intended UX, but does not prove current code or
  deployed-version behavior.

The ranked evidence levels are defined in
`docs/testing/EVIDENCE_LEVEL_POLICY.md`.

## Mandatory conflict record

Every engineering change packet must list each material conflict with:

- the conflicting sources;
- their authority levels;
- whether the conflict affects intent, published identity, implementation,
  qualification, UX, or historical compatibility;
- the evidence that prevents silent reconciliation;
- the owner decision or additional qualification needed;
- the affected implementation scope.

Until resolved, use one of:

- `CONFLICT_VISIBLE_NON_BLOCKING` when the approved change does not rely on the
  disputed fact;
- `OWNER_DECISION_REQUIRED` when product intent or contract meaning is unclear;
- `QUALIFICATION_EVIDENCE_REQUIRED` when behavior is unclear;
- `STOP_SOURCE_CONFLICT` when proceeding could change an immutable or security
  boundary.

## Domain authority boundaries

- Cloud coordinates Project, Workflow, Capsule, Skill, Resource and Artifact
  metadata, exact bindings, uploaded Progress, and Provider proxy authority.
- The Local Workspace owns concrete execution state, materialized inputs,
  outputs, memory/context, local Progress, and continuation evidence.
- Codex is the currently qualified external Agent Harness.
- Browser actions may change Cloud desired metadata but may not write the Local
  Workspace.
- Artifact handoff is an explicit exact identity/checksum binding followed by
  verified local materialization. There is no auto-latest selection.
- Published Capsules, Skills, Definition Versions, Artifact schemas, and
  historical report bytes are immutable.

## Stop conditions

Stop before implementation when:

- owner intent conflicts with an immutable contract;
- a source conflict affects the proposed state transition or version strategy;
- a change would mutate historical Capsule or Artifact bytes;
- a browser action would write Workspace state;
- a sibling Workflow private path would be read instead of a materialized
  Artifact;
- exact Artifact selection would be replaced by latest/first/display-name
  inference;
- a lower evidence level is being used to dismiss a higher-level failure;
- an unapproved migration, Registry publication, Provider call, security
  boundary, or owner-data operation becomes necessary.

## Generated and local state

Generated build outputs, `.next`, coverage, browser reports, runtime logs,
database files, and `runtime_data/` are not governance sources. Private owner
research material, credentials, `.env` contents, Keychain values, and
long-lived Workspace bytes must never be copied into governance documents.
